# 19 — CI

**Phase:** 3 — Core Experience  
**Status:** Specification (locked)

## 1. Purpose

CI is where the tests run for everyone and the gate decides what merges. This chapter gives the recipe: the commands, what their exit codes mean, and how the same recipe covers your own test step and tests split across machines. It names no CI provider; `docs/ci/` shows the recipe for particular providers, as labelled examples.

## 2. The recipe

```text
use-cases verify --run        run the tests (use-cases-bridge.yml) and record their verdicts
use-cases status --gate       does anything block?  (--strict on release branches)
```

| Step | Exit 0 | Exit 1 | Exit 2 |
|---|---|---|---|
| `verify --run` | the run was sealed with no run errors (or no validations are set up: a note says so) | sealed with run errors: a build failure, a missing report, a transformer error | refused: an INVALID workspace |
| `status --gate` | nothing blocks | something blocks (chapter 16 §10) | refused |

**Install first.** The recipe needs `use-cases` on the CI machine, and the install is one pinned step before the commands above (ADR 039): download the release tarball for the runner's platform from the release of tag `v<version>`, check it against the checksum published beside it, and unpack it.

```text
platform   macos-universal  ·  linux-x86_64  ·  linux-arm64
download   use-cases-<version>-<platform>.tar.gz  and  use-cases-<version>-<platform>.tar.gz.sha256
check      the tarball's sha256 equals the one in the .sha256 file; a mismatch fails the job
unpack     into one folder, and put that folder's program on the PATH (a link to it is enough)
```

- **Pinned:** the version is written in the pipeline and changed on purpose, never "latest", so a new release cannot change a job nobody touched.
- **One folder:** the program finds the files shipped with it beside itself, so the tarball is unpacked whole, not just the program copied out.
- Every machine of a split run (section 6) takes the same pinned version.

Then run the commands above in that order, and stop at the first failure. A failing test is not a `verify` failure: it is a verdict, and the gate decides whether it blocks.

## 3. Fresh every run

CI relies on no earlier state. A CI job starts from a clean checkout, with no `.use-cases/`, and the gate judges only what that job's run proved:

- a use case whose tests ran has this run's verdict;
- one whose tests did not run, or that is proved only by hand (`use-cases record`), is `unverified`;
- nothing is ever `stale` in CI, because stale needs an earlier verdict to have gone out of date.

So the default gate blocks on what failed or errored in this run and warns on anything unproven. `--strict` also blocks on unproven: a route proved only by hand cannot pass a strict gate in CI, so such routes are marked `gates_verification: false` (chapter 06) or gated on release branches where someone records them.

Nothing needs to be cached or restored between CI runs. Keeping `.use-cases/runs/` as a CI artifact is useful for people inspecting a failure (the reports, consoles and verdicts are all in it, chapter 12), but no later run reads it.

## 4. Release branches

```text
use-cases status --gate --strict                   everything gating must be proven
use-cases status --gate --strict --group release   only the release group, strictly
```

## 5. Your own test step

When the CI job runs the tests itself instead of `verify --run`, it wraps that step in `--start` and `--finish`:

```text
use-cases verify --start --json      → the run id, and each validation's {report} path
<your test step>                     writes its report to that path
use-cases verify --finish            reads it, judges, seals
use-cases status --gate
```

The path comes from `--start`'s JSON (`reports.<validation id>`). Example recipes read it with a JSON tool and pass it to the test step.

## 6. Tests split across machines

Tests sharded across several CI machines are one run (chapter 13 §16):

```text
job 1   use-cases verify --start --json     keep the run id; save .use-cases/runs/<run id>/ as an artifact
shards  each tests the same commit and writes one uniquely named file, such as shard-3.xml
job 2   restore .use-cases/runs/<run id>/, put every shard's file into its reports/<validation id>/,
        then use-cases verify --finish --run-id <run id>, then use-cases status --gate
```

- The validation has no `report` name, so `{report}` is a folder and every shard's file belongs to one report (chapter 10 §7).
- Shards split the tests between them (by file, or by the test tool's own splitting), so each test runs in exactly one shard. A test that a shard skips because another shard owns it would count as `incomplete`.
- Every job checks out the same commit. `--finish` compares the finish job's code with the start point, and a difference there gets "code changed during the run"; the core cannot see a shard's checkout, so the pipeline must give every shard the same commit.

## 7. Recipes

`docs/ci/` holds the recipe for particular CI providers: the simple run, your own test step, and sharded tests. They are examples. Each names the provider it is for, and each command in them is checked against this chapter's commands.

## 8. Final model

```text
clean checkout ─▶ use-cases verify --run ─▶ use-cases status --gate [--strict] ─▶ merge or not
                   (or --start / your tests / --finish)
                   (or --start / shards / --finish --run-id)

no state from earlier runs · nothing stale · unproven = warning (strict: blocks)
```
