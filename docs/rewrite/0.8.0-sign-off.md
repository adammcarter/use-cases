# 0.8.0 — sign-off package

ADR 0007 decision 9: *no releases during the work; 0.8.0 is cut once everything
is done and the owner has signed it all off.* This is the packet for that
sign-off. It states what changed, what is proven and how it was proven, what is
knowingly **not** proven, and the exact steps that would cut the release.

**Nothing here has been released.** No tag has been pushed, no release created,
no asset published. The version bump sits in the working tree.

## 2. The one thing that changes behaviour the moment this lands

**The version bump is the cut-over.** `bin/use-cases-runtime` branches on the
plugin's own version: `>= 0.8.0` goes to the bootstrap and downloads; below it,
nothing runs. So the instant `.claude-plugin/plugin.json` says `0.8.0`, every
installed host stops using anything local and tries to fetch the release.

Measured here, just now, against the real internet:

```
$ ./bin/use-cases version
use-cases: could not reach https://github.com/adammcarter/use-cases/releases/download/v0.8.0/SHA256SUMS
           (curl exit 56: curl: (56) The requested URL returned error: 404).
use-cases: Check the network or a proxy, then run use-cases again; the download is retried on the next run.
$ echo $?
1
```

That is correct behaviour, not breakage — there is no v0.8.0 release yet. It is
also the reason the release must publish its assets **before or as part of** the
tag. Tag first and every installed plugin fails at its first command until the
assets appear.

One rough edge worth knowing: a 404 is reported as "could not reach … Check the
network or a proxy". It is pre-existing wording and it is misleading when the
real cause is a release that does not exist. Not fixed here — it is a behaviour
change and this row does not make those.

## 3. The corpus edits, and the rule that decided each one

The corpus generators were deleted with the TypeScript (ADR 0007 row 10d), so
the recorded corpora **are** the source of truth. A blind search-and-replace of
`0.7.0` would have been wrong, because the corpora hold two different things:

- **outputs** the binary produces *now* — an envelope it writes, `version`
  printing the version, `created_by.version` on an event it appends this second.
  These must move to `0.8.0`.
- **records** — a pre-existing ledger line a command read and carried forward
  unchanged, an event stamped `"tool":"uc"` from the TypeScript era, a frozen
  snapshot standing for what an older install left behind. Rewriting these
  falsifies a record.

Method: bump the source of truth, run every suite, and let each failure name a
value that is an output. Nothing was edited that no test asked for. Across the
nine corpora **503 occurrences moved and 455 stayed**; outside them nothing moved
at all.

| File | Bumped | Kept at 0.7.0 | Why |
|---|---|---|---|
| `…/Markers/MarkersFreshnessGoldenCorpus.swift` | 131 (`.freshness[].wire` → `tool.version`) | 0 | **Output.** The freshness object the binary derives and prints; `tool` is the tool reporting *now*. |
| `…/Markers/Commands/ScanImpactGoldenCorpus.swift` | 50 (`.scan_cases[].steps[].result.status.tool.version`) | 63 | **Output** is the scan result's own `tool`. **Records** are the 42 in the `entries[]` a case materialises before it runs (plus one `steps[].contents`) — the workspace it is handed — and the 20 `precommit_cases[].scan.status.tool.version` values, which are recorded *inputs* to `Precommit.decide`, not something the binary emitted. |
| `…/Markers/Commands/MarkerCommandsGoldenCorpus.swift` | 43 (42 in `tree[]` files the commands wrote, 1 `registry_events[].json`) | 29 | **Output** is a ledger line `bind`/`unbind`/`rebind` appended during the case. **Record** is a line already present in the case's `entries[]` and echoed unchanged into the tree — **12 of the 54 tree occurrences** are exactly that, and were left alone. |
| `…/Markers/Commands/VerifyProveGoldenCorpus.swift` | 11 | 285 | The starkest split, and it is *inside one JSON path*: only **11 of the 225** occurrences in `steps[].files[]` are lines `verify`/`prove` wrote during the case, and the other **214** are pre-existing ledger lines the command read and rewrote byte for byte. (The remaining 71 kept are plain case inputs.) Bumping one of those 214 turns the suite **red** — measured, see §4. |
| `…/Markers/MarkersLedgerGoldenCorpus.swift` | 0 | 76 | Entirely records: registry text fed *in* to the reconciler, parser and schema validator. No case in this file makes the binary mint an event. The suite is green untouched, which is the proof. |

| `UseCasesCLI/…/Entry/MarkerCommandsGoldenCorpus.swift` | 257 | 0 | **Output.** Every occurrence is either a CLI run's `stdout` or a file the run wrote into `tree_after`. Each case starts from a `setup` that contains no version at all. |
| `UseCasesMCP/…/Server/McpGoldenCorpus.swift` | 5 | 0 | **Output.** `serverInfo.version` in the `initialize` responses. |
| `UseCasesCore/…/Skills/SkillsGoldenCorpus.swift` | **0** | 2 | **Record — and a disclosure.** Its `shipped` map is a *frozen snapshot* of the repository's own files taken in the TypeScript era, used as an input fixture to the skill-asset validator. The validator never reads `version` (`SkillHostRegistration` reads only the skill roots and the marketplace listing), so the value is inert and no test depends on it. Left as the record it is, but see §5: nothing joins this snapshot to the live files, so it *will* drift further. |
| `.use-cases/bindings.jsonl` | **0** | 338 | **Record, and append-only.** 338 past `created_by.version` entries from the 0.7.0 era. Rewriting an append-only ledger is the one edit that would be indefensible. Untouched. |

### The version, by hand, through all three surfaces

### A mixed ledger: new events say 0.8.0, old ones still say 0.7.0

A scratch workspace was seeded with one ledger line recorded in the TypeScript
era, then a real `bind` was run against it. Both lines, from the same file,
after the bind:

```
{… "created_by":{"tool":"uc","command":"bind","version":"0.7.0"},        "row_id":"example.feature.legacy_path" …}
{… "created_by":{"tool":"use-cases","command":"bind","version":"0.8.0"}, "row_id":"example.feature.happy_path" …}
```

The old line is untouched — tool name and version both. That is the corpus rule
of §3, demonstrated on a live ledger rather than a recording.

### Two mutation tests, one in each direction

The output-vs-record split is not an opinion; it was falsified both ways
against `VerifyProveGoldenCorpus`, the file with the sharpest split (11 outputs,
214 records).

1. **A record was bumped to 0.8.0** → `VerifyProveTests` **failed**. So those
   214 occurrences really are pre-existing lines the binary must reproduce
   unchanged, and leaving them alone was required, not merely safe.
2. **An output was reverted to 0.7.0** → `VerifyProveTests` **failed**. So those
   11 really are lines the binary writes now, and bumping them was required.

Both were restored and the suite re-run green.

### The parity test was proved to fail

`.codex-plugin/plugin.json` was set back to `0.7.0`; both parity tests went red
naming that file. Restored and re-run green. The test is load-bearing, not
decorative.

## 5. What is knowingly NOT proven

This is the honest list. None of it blocks the bump; all of it is the owner's
to weigh.

### Two workflows have never run

- **`.github/workflows/release.yml`** — built in row 6 and never fired. It is
  what would build, archive, checksum and attach the assets. It has only ever
  been *read* by tests (`ReleaseWorkflowTests` asserts its text). Its
  `runs-on: macos-15` label is asserted only as `/^macos-/`, deliberately, so it
  does not rot the suite — **check it against GitHub's current runner labels
  before firing it for the first time.**
- **`.github/workflows/use-cases.yml`** — the AUTHORITY workflow, the only thing
  that can mint FRESH. It was rewritten in row 10d because every job began with
  `pnpm install` and would have failed at the first step, meaning no row could
  ever reach FRESH again. The rewrite builds the CLI from source on `macos-15`.
  **Unproven until GitHub runs it.** Nothing local can fire it and no Swift test
  reads it beyond grepping for `gh release`.

The consequence: the first real run of the release is also the first test of the
release pipeline. Firing `release.yml` by `workflow_dispatch` defaults to
`--draft`, which is the cheap way to find out.

### `validate-ledger --base-ref` is vacuous

The append-only check runs `git show <ref>:<path>` with an **absolute** path,
which git always refuses; the code matches that refusal, returns an empty base,
and then compares the ledger against nothing — which can only pass. Measured on
both ledgers. It is a faithful port of the TypeScript, so decision 8 covers it
and row 10d deliberately did not fix it. **The consequence is that
`append_only: true` in CI proves nothing today.** Owner's call whether that is a
0.8.1 fix or a contract change.

### Two places where the code and its own published schema disagree

Decision 8 freezes both the schema and the behaviour, and in two places they
contradict each other. Both are pinned as-is by tests that assert the *rule*, so
a third case appearing would still break the suite.

- **A derived freshness status can fail `ucase-freshness-status-v1`** — a row
  carrying `variant_local_status` (the schema has no member for the variant
  roll-up) and a row whose `row_id` is the empty string. The TypeScript did the
  identical thing; nothing on either side ever validated a derived status, which
  is why it was invisible. Pinned by `FreshnessContractTests`.
- **Presentation plans can likewise fail their own published schema** — four
  shapes, recorded in the row 3f notes.

Left for after 0.8.0, as the notes say. Which side is wrong is the owner's call,
and fixing either is a contract change.

### The hosts' live observations are stale

The four hosts' `edge_live_session` observations were performed on 2026-09-16
against `{"command": "node", "args": ["…/dist/uc-mcp.js"]}`. The command is now
`bash`. The by-hand proof simulates each host exactly — the manifest's own
command and args, from a clean shipped copy, the server answering 19 tools, `ps`
naming the server rather than `bash` — but it **cannot show that the host itself
accepts `command: "bash"`**. Both are bare `PATH` lookups so the risk is low,
but the re-observation (install on Claude and Copilot, start a session, list the
MCP tools) is still owed. Codex's live MCP observation has never been made at
all.

### The download path is proved only against a stand-in

Every bootstrap and release test drives a local stand-in release, because no
real one exists. The real fetch-verify-cache-exec path against
`github.com/adammcarter/use-cases/releases` has never run end to end. §2's 404
is the closest thing to a live test so far, and it only proves the *refusal*.

### Row 9's left-undone list

Row 9 enumerated 133 white-box files and wrote tests for the highest-value gaps.
What it did not carry over is written out in full in
[`ladder-notes.md` § "Left undone, and it is a real list"](ladder-notes.md) —
roughly 30 items. The ones worth the owner's eye:

- **The 0.5.5 upgrade contract.** `tests/fixtures/backcompat/proven-0.5.5/` is a
  real artifact of a published binary and is touched by **no** Swift test. Row 9
  calls it the highest-value item on the list. The fixtures survive; only the
  harness died.
- **No Swift test schema-validates real command output.** The corpora compare
  bytes; nothing checks a command's real `--json` against
  `cli-result.schema.json` or its `data` against its own schema.
- **The `use-cases-mcp` executable has no test.** `McpGoldenCorpusTests` calls
  the server in-process; nothing launches the binary, so `--stdio` framing over
  real pipes, id matching and "closing stdin ends the process" are pinned by
  nothing. (The by-hand `initialize` in §4 is the only thing that has ever
  driven the real executable — once, today.)
- **Two anti-drift joins have both halves in Swift and nothing joining them** —
  `KnownCliCommands` × `CommandRegistry.allCommands`, and
  `McpToolCatalog.descriptors` × `CommandRegistry.allCommands` (which is what
  keeps the CLI-only trust surface off the MCP).
- **The shipped skills and agents are pinned only by a frozen snapshot.**
  `SkillsGoldenCorpus.shipped` is a TypeScript-era capture; editing a real skill
  or agent body today fails no Swift test. This is also why that corpus still
  says `0.7.0` (§3) and why it will keep drifting.

### The six oracle todos

Listed in the run and reported as skipped with their reasons; they cannot go
green by accident. They are a host observation, one row claiming behaviour the
tool lacks, `matrix list` not projecting usage/scenario, and three
`revision_epoch_staleness` scenarios for which no CLI command exists.

## 6. To cut the release

**None of these steps has been taken.** They are written out so the sequence is
deliberate; the ordering in particular is not optional.

1. **Read and accept `CHANGELOG.md`.** It is the user-facing contract for what
   breaks. Correct anything you would say differently — it is easier now than
   after the tag.
2. **Check `runs-on: macos-15` is still a live GitHub runner label** in
   `release.yml` and `use-cases.yml`. The suite deliberately does not pin it.
3. **Commit the working tree.** Row 11's changes are unstaged by design: this
   agent does not commit, per the brief.
4. **Fire `release.yml` by `workflow_dispatch` first.** It defaults to
   `--draft`, so this is the safe first run of a pipeline that has never run.
   Confirm it produces `use-cases-0.8.0-macos-arm64.tar.gz` and `SHA256SUMS`,
   that the archive carries **both** executables, and that `lipo -info` reports
   a thin arm64 Mach-O.
5. **Publish the release.** The assets must exist before the tag is what hosts
   resolve — see §2.
6. **Then tag `v0.8.0` and push it.** A `v<semver>` tag push is the workflow's
   other trigger; there is no `branches:` key, so a branch push can never
   publish.
7. **Prove the real download once.** On a clean machine, or with
   `USE_CASES_CACHE_DIR` pointed at an empty directory:
   `./bin/use-cases version` should print `0.8.0` after fetching and verifying.
   This is the first end-to-end test of the path in §5.
8. **Re-observe the four hosts.** Install the plugin on Claude and Copilot,
   start a session, list the MCP tools. That closes the stale `edge_live_session`
   observations and the never-made Codex one.
9. **Tell adopters what §"Removed" of the changelog says**, especially that a
   `uc` in their own git hooks now fails silently from the plugin's point of
   view, and that the fix is `use-cases init`.

## 7. Questions for the owner

1. **The vacuous append-only check** — fix it in 0.8.1, or accept that
   `append_only: true` means nothing and say so in the docs?
2. **The freshness and presentation-plan schema disagreements** — which side is
   wrong? Fixing either is a contract change, so it is a 0.9.0 question rather
   than a 0.8.x one.
3. **The 0.5.5 upgrade contract** — worth a Swift harness? The fixtures survived
   the deletion precisely so this stays possible.
4. **The frozen skills/agents snapshot** — should a test join
   `SkillsGoldenCorpus.shipped` to the live `skills/` and `agents/` trees? Today
   they can part with nothing noticing, and this bump is the first visible
   symptom.
5. **The 404 wording** in the bootstrap (§2) — worth a clearer message for "this
   release does not exist" versus "the network is down"?
